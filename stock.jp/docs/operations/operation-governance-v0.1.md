# 日本株運用ガバナンス v0.1

- 発効日: 2026年8月31日
- 現在の運用モード: `PAPER`
- 現行PAPERベースライン: `v0.4`
- シャドー比較: `v0.2`、`v0.3`
- 発注権限: `HUMAN_ONLY`

## 1. 正本と優先順位

運用可否と使用ルール版は、親のprivateリポジトリで追跡する `operations/private/operation-policy.json` を正本とする。初期値は `PAPER` であり、調査、判定、仮想注文、反実仮想の記録だけを行う。`PAPER` の注文票は `PAPER_PROPOSED` とし、証券会社へ入力しない。

`v0.4`は、利用者がこの運用へ与えた資金の100%をテンバガー戦略資金とし、固定的な安全資産枠を0%にする現行PAPERベースラインである。資金配分以外は`v0.2`を引き継ぐ。`v0.2`と`v0.3`はシャドー比較専用とし、日次の注文判断には使わない。`v0.4`を実資金へ使用するには、[v0.4のPAPER検証とLIVE昇格](../rules/tenbagger-rule-v0.4.md#6-paper検証とlive昇格)を満たし、2025〜2026回顧的replayとは別に、v0.4凍結後の未観測期間を事前登録した`v04_holdout_promotion`と承認ログを残す。実運用手順、スキル、日次プロンプトが本書と競合した場合は本書を優先する。

`v0.4`の未投資現金はすべて`戦略待機資金`であり、安全資産または運用対象外資金とは扱わない。合格候補不足、追加購入の四半期条件待ち、`MRS`、流動性、100株単位、注文費用のために一時待機できるが、固定的に一定比率を残す規則は設けない。

## 2. `LIVE` 昇格ゲート

次をすべて満たすまで `operation_mode` を `LIVE` にしない。

1. 上場廃止を含むpoint-in-time全母集団で入口・出口を検証した
2. 2025年通年と2026年1月1日から8月31日までを、当時利用可能だった情報だけで再生し、銘柄別・年別・合計の損益、最大ドローダウン、売買履歴、欠損を利用者が確認して明示承認した
3. 最新の完了済みv0.4 PAPER runで必須の公式情報源を機械取得または網羅確認できる
4. private repository の clean-clone 復旧試験に成功した
5. 利用者が損失許容予算、税区分、証券会社の注文仕様、注文可能時間を確認した
6. 利用者が承認者と承認日時を記録した

使用版が `v0.3` の場合は`v03_holdout_promotion`、`v0.4`の場合は`v04_holdout_promotion`が必要である。PAPERの経過日数と連続run数はLIVEゲートにせず、一律の365日または20営業日の完了を待たない。ただしv0.4のforward holdoutは、本人が結果を見る前にplanへ固定した期間と最低観測数を完了しなければならない。ゲートはチャット上の宣言ではなく、`operation-policy.json`の真偽値と根拠パスで確認する。

2番の履歴再生は、未来情報を使わず、2025年と2026年の各月末時点に存在した全対象銘柄、上場廃止、合併、分割・併合、当時公表済みの財務・開示、情勢指数、注文可能性、売買費用を含める。必須入力が欠けた銘柄を有利に除外せず `WAIT` と欠損率を報告する。現存銘柄だけ、事後に判明した上昇銘柄だけ、または価格系列だけの検証ではこのゲートを満たさない。正本となる検証状況は[2025–2026年履歴再生](../research/historical-replay-2025-2026.md)へ記録する。

`LIVE` へ昇格しても発注権限は `HUMAN_ONLY` のままとする。夜間エージェントは翌営業日の注文候補を作成し、人間が注文前チェック後に証券会社へ入力する。

### LIMITED_LIVE

通常LIVE前の少額実約定は[LIMITED_LIVE](limited-live-v0.1.md)として分離する。
専用資金上限、本人の累積損失停止、1 run 1新規注文、追加購入禁止を強制し、
公式source coverage、clean-clone、個人checklistが合格した場合だけPAPERから昇格できる。
この段階はpoint-in-time履歴、forward holdout、最終LIVE承認を完了したことにせず、
通常LIVEへの自動昇格も行わない。

## 3. 夜間実行の行動制限

| モード | 調査 | 判定 | 注文票 | 証券会社への入力 |
|---|---|---|---|---|
| `PAPER` | 実施 | 実施 | `PAPER_PROPOSED` | 禁止 |
| `LIMITED_LIVE` | 実施 | 実施 | `PROPOSED`（1 run 1新規・追加禁止） | 人間だけ |
| `LIVE` | 実施 | 実施 | `PROPOSED` | 人間だけ |
| `PAUSED` | 取得漏れ・既存リスクだけ確認 | `WAIT`優先 | 作成禁止 | 禁止 |

データ不足、ルール版不明、台帳不整合、注文重複、公式情報源未確認の場合は、モードに関係なく新規・追加注文を作成しない。既存保有の重大リスクは `WAIT` で隠さず、確認済み事実と未確認範囲を報告する。

## 4. ルール見直しの周期

日次運用とルール変更を分離する。

| 周期 | 確認内容 | 閾値変更 |
|---|---|---|
| 日次 | 情報源、判断、注文、台帳の例外 | 禁止 |
| 月次 | 実行成功率、取得漏れ、重複、ルール遵守率、約定差異 | 禁止 |
| 四半期 | 実現・含み損益、最大DD、候補数、見送り反実仮想、条件別損失回避・機会損失 | 禁止。変更仮説だけ登録 |
| 暦年終了時 | 固定済み評価指標でベースラインとチャレンジャーを比較 | 条件を満たす新版だけ審議 |

レビュー結果は `operations/private/rule-review-log.csv` へ1回1行で残す。改善案は「対象とする誤り」「変更する層」「主評価指標」を1つずつ事前登録する。凍結済み文書を上書きせず、新しい版を作る。同じ未見期間を見て閾値を再調整しない。

## 5. 変更手順

1. 現行版、データカットオフ、試行番号を固定する
2. 運用上の不具合と投資仮説の不成績を分ける
3. 改善仮説と棄却条件を結果を見る前に記録する
4. 発見用期間だけでチャレンジャーを実装する
5. パージ期間後の未見期間で一度だけ比較する
6. 昇格、棄却、継続観察のいずれかを記録する
7. 昇格時は既存保有へ新旧どちらを適用するか移行方針を記録する

日々の損益や1件の成功・失敗を理由にルールを変更しない。
